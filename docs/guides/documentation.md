# 文档写作与维护

返回[文档入口](../README.md)。目标是让读者从真实修改任务找到代码、规则和验证方式；不要求为每个函数再写一份说明。

## 内容归属

架构写约束，Code map 写实现位置，前端规范写交互与验收，指南写操作步骤，决策写理由与代价，路线图写未完成方向。完整描述只保留一处，其他文档链接引用。当前状态以源码和测试核对；与已采纳规范不一致时记录偏差，不能通过更新地图掩盖未实现要求。

已完成计划先提取有效规则，再移入 archive，并更新所有入链。被取代的决策保留日期和背景，明确替代关系。发布记录保留版本语境，不跟随当前能力改写。

## Code map 模板

```markdown
# 领域名称

返回总地图；链接到本领域架构规范。

## 职责与边界

负责什么，依赖方向是什么，职责止于哪里。

## 关键入口

列出少量文件链接、核心符号和作用；兼容出口与生产入口明确区分。

## 主要调用链

用短列表或小图追踪一次真实操作，包括结果和事件返回路径。

## 状态与契约

谁拥有状态，在哪里校验，是否持久化，失败或取消后如何收敛。

## 修改指引

常见修改涉及哪些位置，容易遗漏哪些边界。

## 验证入口

链接到相关测试，说明它验证什么；复杂规则链接到规范和决策。
```

## 写法与更新触发

- 中文解释，保留可搜索的英文类型、方法与工具名；使用稳定标题和仓库相对链接。
- 源文件和测试路径写成 Markdown 链接，让工具验证存在性。目录表只列模块和入口，完整类型、SQL、默认值以源文件为准。
- 少依赖行号；调用链节点标核心符号即可。图控制在一条主流程内，避免生成不可阅读的全仓库 import graph。
- 对保留代码明确“可用／暂停／未实现”，并链接当前产品范围；不要把旧阶段未勾选清单当待办。
- 模块移动、公共入口、跨层调用、状态所有权变化时更新地图；规则变化时更新所属规范，重要取舍追加决策。局部实现修复不必改无关页面。
- 页面过长时按读者问题拆专题，保留入口页；同一段规则不在 requirements、architecture 和地图重复展开。

## 自动检查

`npm run format:docs` 与 `format:docs:check` 覆盖根 README、AGENTS、`docs/**/*.md` 和 Tooling README。产品 Prompt 资源和设计素材文档不在自动格式化范围，避免改变模型输入或外部素材。

`npm run check:docs` 验证上述维护范围中的本地 Markdown 链接、图片、目录和标题锚点，并运行检查器回归测试。检查器与 Prettier 都遵守 `.gitignore` / `.prettierignore`，本地 `docs/code-review-report` 不纳入维护。文件与代码行锚点会检查存在性/范围；远程 URL 不发网络请求，代码块与 inline code 中的示例不作为链接。

`npm run format` / `format:check` 包含文档格式，`npm run check` 包含文档链接检查。引用符号是否仍承担描述的职责、行为是否与规范一致，仍由修改者按源码和测试复核；链接检查不能替代语义审查。

## 整理验收

从[任务索引](../code-map/README.md#按修改任务查入口)分别尝试新增工具、修改设置、排查状态同步和调整后台取消：每条都应能到达当前入口、相关约束与回归测试。不存在的文件、被移走的规范和暂停功能不能作为未标注的开发入口。
